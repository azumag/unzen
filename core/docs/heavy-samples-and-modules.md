# 重い処理サンプルとモジュールシステム設計

## 概要

6エージェント（architect/opus, designer/sonnet, skeptic/sonnet, product-thinker/haiku, security-perf/haiku + researcher/sonnet）による多角的議論の結果をまとめた設計文書である。

**議論の結論**: Unzenの方向性を「一般的な計算委譲フレームワーク」から「安全なサンドボックス実行システム」へピボットすべきである。Phase 0（実証検証）→ Phase 1（MVP + 重い処理サンプル）→ Phase 2（モジュールシステム）の段階的アプローチを採用する。

> **除外: CSVパース** — フロントエンド直接実装が適切。

> 計算根拠が不透明であったため削除。実際の純CPU時間コストは
> `CPU時間/回 × リクエスト数/月 × 12 ÷ 3,600,000 × 時間単価` で求められ、
> 上記の想定規模では数十ドル/年程度となる。コスト削減の主張には
> 実測ベンチマークと実際のトラフィック規模に基づく検証が必要。

### サンプル詳細

#### 1. PBKDF2パスワードハッシュ計算
- **説明**: サインアップ時にクライアント側でパスワードをハッシュ化する
- **アルゴリズム**: SHA-256を純粋JSで実装 → HMAC-SHA256 → PBKDF2 (RFC 2898)
- **メモリ**: ~1MB以下
- **コード量**: ~200-300行
- **Unzenに適する理由**: 自己消費（自分のパスワード）、プライバシー向上（平文がサーバーに送信されない）
- **注意**: QuickJS Wasmで1.75-4.4秒はローディング表示必須。サインアップは低頻度なので許容できる

#### 2. 大規模配列ソート
- **説明**: データテーブルUIでの10,000-50,000行のマルチキーソートを行う
- **アルゴリズム**: Array.prototype.sort + カスタム比較関数
- **メモリ**: ~10MB (10K行×10カラム×100byte)
- **コード量**: ~50-100行
- **Unzenに適する理由**: 高頻度操作（1セッションで複数回）、インタラクティブUI
- **推奨理由**: 実装が容易で、汎用性が高い

#### 3. 画像メタデータ抽出（EXIF）
- **説明**: アップロード前に画像のEXIFデータを抽出し、GPS位置情報を除去する
- **アルゴリズム**: JPEG APP1マーカー + TIFF形式のEXIF解析、PNGチャンク構造パース
- **メモリ**: ~6MB
- **コード量**: ~300-400行
- **Unzenに適する理由**: プライバシー（GPS位置情報をサーバーに送信せず除去）

#### 4. 大規模Markdown変換
- **説明**: 10,000行以上のMarkdownのGFM準拠レンダリングを行う
- **アルゴリズム**: Lexer/Parser/Renderer パターン
- **メモリ**: ~6MB (AST含む)
- **コード量**: ~800-1000行
- **Unzenに適する理由**: 最高頻度（エディタで数秒おきにプレビュー更新）

#### 5. JSONスキーマバリデーション
- **説明**: JSON Schema Draft-07準拠の入力検証を行う（100プロパティ、50ルール）
- **アルゴリズム**: 再帰的スキーマトラバーサル
- **メモリ**: ~2MB
- **コード量**: ~500-700行
- **推奨理由**: 最大のコスト削減効果、不正リクエストがサーバーに到達しない

#### 6. テキスト類似度計算（Levenshtein距離）
- **説明**: 10,000文字×2テキストの編集距離を計算する（重複検出）
- **アルゴリズム**: 動的計画法 O(n×m)、メモリ最適化版 O(min(n,m))
- **メモリ**: ~100KB
- **コード量**: ~50-80行
- **Unzenに適する理由**: O(n²)アルゴリズムでサーバーCPU削減効果が大きい

## 1.5. Unzenに適するユースケースの判定基準

Unzenの本質的な優位性は「サーバーがロジックのオーナーシップを持ちつつ、実行コストをクライアントに委任できる」点にある。以下の条件を**複数**満たすユースケースがUnzenに適する。

### サーバー定義→ブラウザ委任の3つの優位性

| 優位性 | 説明 | 具体例 |
|--------|------|--------|
| **ロジックの一元管理** | ビジネスルールの定義をサーバーに集約し、クライアントは実行のみ担当。ルール変更時にフロントエンドの再デプロイが不要 | 価格計算の税率変更、バリデーションルール追加 |
| **改ざん耐性** | QuickJSサンドボックス（frozen prototypes, no eval）により、devtoolsでのロジック改ざんを防止。フロントエンド直接実装では不可能 | 価格計算、割引適用、フォーム検証 |
| **透過的フォールバック** | ブラウザ実行が失敗した場合、同一ロジックがサーバーで自動実行される。開発者はフォールバック分岐を書く必要がない | 全ユースケース共通 |

### 判定フロー

```
そのロジックはサーバーが定義・管理する必要があるか？
  ├─ NO → フロントエンド直接実装（Unzen不要）
  │        例: CSVパース、画像リサイズ、Base64エンコード
  └─ YES
      └─ 改ざんされると問題があるか？
          ├─ YES → Unzenに最適（価格計算、バリデーション）
          └─ NO
              └─ ロジック変更頻度が高いか？
                  ├─ YES → Unzenに適する（フロントエンド再デプロイ不要）
                  └─ NO  → 費用対効果を検討
```

### Unzenに適さないユースケース

以下の特徴を持つ処理は、フロントエンドで直接実装すべき。

| 特徴 | 理由 | 例 |
|------|------|-----|
| 標準アルゴリズムで、ロジックが普遍的 | サーバーが定義を管理する必然性がない | CSVパース（RFC 4180）、Base64エンコード |
| データが既にクライアント上にある | Unzenのネットワーク削減メリットが発生しない | ファイルアップロード前のパース・プレビュー |
| パフォーマンスが重要 | QuickJS Wasmは V8の35-55倍遅い。ユーザー体感に直結する処理には不適 | リアルタイム画像処理、大規模CSVパース |
| 成熟したフロントエンドライブラリがある | 再実装は車輪の再発明 | CSV→PapaParse、Base64→標準API(btoa/atob) |

> **CSVパースが除外された経緯**: 当初Phase 2のheavy sampleとして計画されていたが、
> (1) CSV(RFC 4180)は標準仕様でありサーバー定義の必然性がない、
> (2) ファイルは既にクライアント上にありネットワーク削減効果がない、
> (3) V8で30-50msの処理をQuickJS Wasmで1-2.75秒かけるメリットがない、
> (4) PapaParse等の成熟ライブラリが存在する、以上の理由から除外。

## 2. モジュールシステム設計

### 推奨アプローチ: ビルドタイム npm バンドル方式

#### 5つのアプローチの比較

| アプローチ | Pros | Cons | 推奨度 |
|-----------|------|------|--------|
| A. Unzen独自レジストリ | 完全制御、品質管理可能 | メンテナンスコスト甚大、エコシステム構築に年単位 | x |
| B. npm→Unzen変換ツールチェーン | 既存エコシステム活用 | Node.js API依存パッケージが多数、変換失敗リスク | x |
| **C. ビルドタイムバンドル** | **esbuild/rollupで確立された手法、tree-shaking可能** | **pure ESMのみ対応** | **推奨** |
| D. CDN経由配信 | 設定不要 | バージョン固定困難、ランタイム依存 | x |
| E. "unzen:" prefix | DXが良い | ビルドツール統合の複雑さ | 将来検討 |

#### API設計案（Phase 2向け）

```typescript
// === Phase 1: defineRaw（現状維持、まず価値を実証） ===
server.defineRaw('sortData', `
  function run(data, sortKeys) {
    return data.sort((a, b) => { /* ... */ });
  }
`);

// === Phase 2: define ヘルパー（型安全） ===
import { define } from '@unzen/server';

// TypeScript関数を直接定義（ビルド時にコード文字列に変換）
const sortData = define('sortData', (data: any[], sortKeys: SortKey[]) => {
  return data.sort((a, b) => {
    for (const { key, order } of sortKeys) {
      const cmp = a[key] < b[key] ? -1 : a[key] > b[key] ? 1 : 0;
      return order === 'desc' ? -cmp : cmp;
    }
    return 0;
  });
}, { timeout: 500 });

// === Phase 2: モジュールインポート ===
import { define, useModule } from '@unzen/server';

// npmパッケージをUnzen互換として読み込み（ビルド時にbundle）
const validator = useModule('validator', {
  // ホワイトリスト必須（security-perf提言）
  allowedExports: ['isEmail', 'isURL', 'isCreditCard'],
  maxBundleSize: '100KB',
});

const validateInput = define('validateInput', (input: string, type: string) => {
  const v = require('validator');
  if (type === 'email') return v.isEmail(input);
  if (type === 'url') return v.isURL(input);
  if (type === 'creditCard') return v.isCreditCard(input);
  return false;
}, {
  modules: [validator],
  timeout: 500,
});
```

#### セキュリティ制約（security-perf提言統合）

| 制約 | 値 | 根拠 |
|------|------|------|
| モジュールホワイトリスト | 必須（P0） | サプライチェーン攻撃防止 |
| コンテキスト分離 | モジュールセット単位 | 100回呼出で6.3x遅延 → ハイブリッド方式 |
| バンドルサイズ上限 | 100KB/モジュール | 16MBメモリ制限との整合 |
| モジュール数上限 | 小規模55個/中規模5個/大規模2個 | 16MB制限内 |
| キャッシュ戦略 | IndexedDB (5-20ms) + Service Worker (1-5ms) | コールドスタート最小化 |

#### ビルドパイプライン

```
npm package → esbuild (tree-shake, bundle) → Unzen互換チェック
  → 禁止API検出（静的解析: fetch, XMLHttpRequest, fs, net 等）
  → ハッシュ計算（SHA-256）→ コードキャッシュ登録
```

## 3. 懐疑的分析の要点と応答

### skepticの主要批判

| 批判 | 応答 |
|------|------|
| QuickJS Wasm 35-55x遅いのにサーバーからブラウザに移す価値があるか？ | 500ms-2sの遅延はローディング表示で許容可能。高頻度操作（ダッシュボードソート等）でサーバーCPU負荷を削減 |
| サーバーCPU $0.05/hr vs 開発コスト | 単純なCPUコストではなくスパイク対応コスト（オートスケーリング設定、CDN等）も含めると差が広がる |
| 既存技術（Edge Functions, PWA）で十分ではないか？ | Edge Functionsは**訪問者自身のブラウザ**では動かない。Unzenの差別化は「サーバーレスすら不要」 |
| 純粋関数制約で重い処理は無理では？ | 上記6サンプルは全て純粋関数で実装可能。制約内で十分な実用性がある |
| npmライクなモジュールシステムは車輪の再発明 | Phase 2に延期。Phase 1でまず価値を実証してから投資判断 |

### skepticが認めた有効ケース（5条件を全て満たす場合）

1. **サーバーCPU負荷が実際に高い**（1リクエスト10ms超）
2. **代替不可能な機能がある**（特に第三者コードの安全実行）
3. **ユーザー体験が許容範囲**（ローディング表示で対応可能）
4. **プライバシーメリットがある**（データがサーバーに送信されない）
5. **開発者にとって採用コストが低い**（既存ツールチェーンとの統合）

## 4. プロダクト視点

### ターゲットペルソナ

| ペルソナ | 説明 | 優先度 |
|---------|------|--------|
| Persona A | プライバシー重視のインディー開発者 | 高 |
| Persona B | リアルタイムUX重視のECサイト開発者 | 高 |
| Persona C | エンタープライズ | 当面対象外 |

### 方向性のピボット

```
修正前: 一般的な計算委譲フレームワーク
修正後: 安全なプラグイン/サンドボックス実行システム
```

**差別化ポイント**:
- Edge Functions/Cloudflare Workersとの違い = 「訪問者のブラウザ内」で実行する
- Partytownとの違い = 「サーバー定義関数のサンドボックス実行」
- 唯一の価値 = **第三者コードの安全実行保証**（eval/Function/Proxy/Reflectブロック + prototype freeze）

### DX改善（Phase 1）

```typescript
// 現在: DXが悪い
server.defineRaw('sortData', `function run(data) { ... }`);

// Phase 1改善: 型安全ヘルパー
import { define } from '@unzen/server';
const sortData = define('sortData', (data: any[]) => {
  // 通常のTypeScript関数として記述
  return data.sort(/* ... */);
});
```

### キラーデモ候補（マーケティング角度）

1. **"Your Server Bill, Halved"** - ダッシュボードソート + JSONバリデーションの組み合わせデモ
2. **"Zero-Knowledge Form Validation"** - パスワードが平文でサーバーに送信されないデモ
3. **"Hot-Update Business Rules"** - サーバー側の価格計算ルールを変更し、フロントエンド再デプロイなしで即座に反映されるデモ

## 5. 実装ロードマップ

### Phase 0: 実証検証（4-6週間, 160時間上限）- skeptic+designer合意

- [ ] 実験環境構築（ベンチマークフレームワーク）

4. **バッテリー消費**: 体感できないレベル
5. **セキュリティ**: devtools改ざん対策の有効性確認

## 6. クロスディスカッションの軌跡

エージェント間の直接対話で以下の合意形成プロセスが進行した。

### ラウンド1: 個別分析（各エージェントが独立に調査・提案）
- architect: 重い処理サンプルのリサーチ（スタック発生）
- designer: モジュールシステム設計提案（アプローチE推奨）
- skeptic: 7セクション構成の徹底批判
- product-thinker: ペルソナ定義、DX改善案
- security-perf: メモリ制約・キャッシュ戦略分析

### ラウンド2: クロス議論（エージェント間直接メッセージ）
- **skeptic → designer**: モジュールシステムへの6点批判（lodash.debounceケーススタディ）
- **designer → skeptic**: 技術的反論（ビルド時バンドルの正当性、既存ツール活用）
- **skeptic → product-thinker**: 経済性以外の価値も検証不足と指摘
- **product-thinker → skeptic**: 方向性修正提案「計算委譲→安全なプラグイン実行」
- **security-perf → designer**: コンテキスト分離オーバーヘッド(6.3x)とハイブリッド方式提案

### ラウンド3: 合意形成
- **skeptic**: 「技術的正しさは認める。実用的価値の実証が必要」→ Phase 0提案
- **designer**: skepticの批判を全面受容、Phase 0計画策定、security-perf制約統合
- **product-thinker**: 「安全なプラグイン実行システム」への方向性修正に全員合意
- **skeptic**: designerのPhase 0計画に3つの改善を追加（早期失敗検出、インタビュー、コスト上限）
- **designer**: 改善を全て採用し最終版を作成

### 最終コンセンサス
全エージェントが以下に合意:
1. Unzenの価値は「計算委譲」ではなく「安全なサンドボックス実行」にある
2. Phase 0実証が必須（実測データなしに実装を進めるべきではない）
3. モジュールシステムはPhase 2に延期（まず基本的な価値を証明）
4. 失敗時は潔く中止する（技術デモとして公開は許容）
