# Swarm Intelligence × 軽量LLM 設計書

## 本文書の位置づけ

PLAN.md v2.6 で確定した30Bモデル×パイプライン並列方式に対する**補完的アプローチ**として、1.2Bクラスの軽量モデルを群知能で協調させる設計を記載する。

パイプライン方式（既存）と群知能方式（本文書）は排他的ではなく、併用を前提とする。

---

## 1. 既存方式との対比

| 項目 | パイプライン方式 (PLAN.md) | 群知能方式 (本文書) |
|------|--------------------------|-------------------|
| モデルサイズ | 30B (4-bit, ~17GB) | 1.2B (4-bit, ~600MB) |
| ノード要件 | 1ノードあたり~2.1GB VRAM | 1ノードあたり~600MB VRAM |
| モデル分割 | 8セグメントに分割 | **分割不要（各ノードが完全なモデルを保持）** |
| 協調方式 | 中央集権Coordinator | **分散型Gossipプロトコル** |
| 品質の源泉 | 大規模モデルの能力 | **集合知（複数の独立評価の集約）** |
| チェックポイント | セグメント間で転送が必要 | **不要** |
| 障害耐性 | Coordinator障害で全体停止 | **個別ノード障害を吸収** |
| 対象端末 | WebGPU対応の高スペック端末 | **CPU推論含む幅広い端末** |

## 2. 群知能の生物学的背景

本設計で参照する自然界の群知能パターン:

### 2.1 ミツバチの巣選び（Quorum Sensing）

```
偵察蜂が候補地を独立に探索
→ 帰巣して「尻振りダンス」で評価を共有
→ 良い候補地ほど多くの蜂が支持
→ 閾値を超えた候補地に群れが移動

対応: 各ピアが独立に応答を生成し、相互評価スコアが
閾値を超えた提案が最終出力として選択される
```

### 2.2 アリのフェロモン経路（Stigmergy）

```
個々のアリが経路にフェロモンを残す
→ 良い経路ほどフェロモンが蓄積
→ 後続のアリは濃いフェロモンの経路を選好
→ 最適経路が創発的に発見される

対応: ピアの評価スコアが「フェロモン」に相当し、
高評価の提案に支持が集まることで品質が創発する
```

### 2.3 Boidモデル（群れの行動規則）

```
3つの単純なルールから複雑な群れ行動が創発:
  分離: 近すぎる個体から離れる（重複回避）
  整列: 近隣個体と速度を合わせる（合意形成）
  結合: 群れの中心に向かう（品質基準の維持）
```

## 3. アーキテクチャ

### 3.1 全体図

```
API顧客
  │
  ▼
[Relay] ← 状態を持たないメッセージ中継（unzenインフラ）
  │
  ├──── Peer A (1.2B model, Browser)
  ├──── Peer B (1.2B model, Browser)
  ├──── Peer C (1.2B model, Browser)
  ├──── Peer D (1.2B model, Browser)
  └──── Peer E (1.2B model, Browser)

各Peer:
  - 完全なモデルをローカルで実行
  - 独立に応答を生成
  - 他ピアの応答を相互評価
  - Gossipプロトコルで情報交換

Relay:
  - メッセージの中継のみ（ルーティング判断をしない）
  - 状態を持たない（任意のリレーが代替可能）
  - PLAN.md 1.2の通信制約を維持
```

### 3.2 推論フロー

```
Phase 1: Scatter（散布）
  タスクが全参加ピアにブロードキャスト
  各ピアが独立に応答を生成（並列実行）

Phase 2: Evaluate（相互評価）
  各ピアが受信した全提案をスコアリング
  自分の提案は評価しない（バイアス排除）

Phase 3: Converge（収束）
  スコアを集約（平均 or 信頼度加重平均）
  閾値を超える明確な勝者が出れば合意成立
  出なければ最高スコアの提案を採用
```

### 3.3 なぜ1.2Bモデルの相互評価が機能するか

研究知見（Zheng et al. 2023 "Judging LLM-as-a-Judge" 等）:
- 小規模モデルでも、「生成」より「判別」の方が得意
- 複数候補から最良を選ぶタスクは、ゼロから最良を生成するより容易
- N個の独立評価の平均は、個々の評価より安定する（大数の法則）

### 3.4 現在の実装状況

**重要**: 現在の `Swarm` クラスは群知能ライフサイクルの**中央集権的シミュレーション**である。各フェーズ（scatter/evaluate/converge）を同期的にオーケストレーションしており、実際のGossipメッセージ交換はまだ実装されていない。

目的は、コアアルゴリズム（複数エージェントサンプリング + 相互評価 + 合意形成）の正しさを検証してから、分散型Gossip実装に投資すること。

## 5. 経済性の考察

### 5.1 VRAM要件の緩和

```
パイプライン方式: 2.1GB VRAM / ノード → WebGPU対応の中〜高スペック端末のみ
群知能方式:      ~600MB VRAM / ノード → CPU推論も現実的

→ 参加可能なデバイスプールが大幅に拡大
→ PLAN.md 3.3の公平性問題（WebGPU非対応端末）を部分的に解決
```

### 5.2 トレードオフ

```
利点:
  - 参加デバイスの大幅増（低スペック端末も参加可能）
  - チェックポイント転送が不要（レイテンシ削減）
  - 単一障害点がない
  - モデルの事前ダウンロードが小さい（600MB vs 2.1GB/セグメント）

欠点:
  - 1.2Bモデルの個体性能は30Bより大幅に低い
  - 相互評価のオーバーヘッド（N×N回のスコアリング）
  - 群知能で品質をどこまで上げられるかは未検証
  - APIレイテンシは生成+評価の合計時間に依存

未解決:
  - 1.2B × N のスウォームと単体30Bの品質比較（要実測）
  - N=何台で品質の収穫逓減が始まるか
  - 相互評価のコスト対効果（評価自体がLLM推論）
```
