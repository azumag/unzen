# Browser artifact-budget runtime envelope

The real browser split harness treats artifact-budget inputs as runtime data rather than trusting TypeScript or JSON producers. `planSegmentArtifactBudget()` requires a non-array object before it reads segment fields. `verifyActualSegmentArtifactBudget()` requires an object plan and an array of artifact reports before reduction or budget comparisons.

The planner captures only fields that belong to its runtime preflight (`index`, `browserArtifactBytes`, `externalData`, and artifact load identity when present) from the caller-owned segment, reading consumed values deliberately and preserving fail-fast validation order. In particular, an invalid declared byte count is rejected before the later `externalData` accessor is touched. It deliberately does not spread the whole object, so unrelated enumerable accessors are not executed as a side effect of planning. External-data array membership is detached before entry fields are consumed. Each external-data `bytes`, `location`, and `sha256` field used by browser loading is captured exactly once, and byte arithmetic uses only the owned primitive snapshot. This prevents an earlier external-data entry from replacing a later array element during the same planning pass and prevents accessor-backed entries from changing identity after an awaited browser fetch begins.

When graph `path` or external-data `location` fields are present, the planner also checks them before the browser harness can begin an artifact fetch. Runtime artifact locators must be relative POSIX paths with no empty, `.` or `..` components, backslashes, colon-based drive/scheme aliases, control characters, Windows reserved aliases, trailing Windows dots/spaces, or URL-significant `%`, `?`, and `#` characters. The last three are intentionally stricter than the generated-manifest importer's encoded locator path: `runner-v3.js` currently interpolates manifest paths directly into a URL, so percent escapes, query strings, and fragments must be rejected rather than reinterpreted by the URL parser. Standalone synthetic budget callers may omit artifact load identity entirely or provide locator-only fields for path-confinement tests. Once any SHA-256 field is present, however, the graph and every external-data entry must provide the complete path/digest identity needed to construct `artifactLoad`.

The planner normalizes accepted SHA-256 values to lowercase and returns an owned `artifactLoad` snapshot containing the graph path, digest, and declared bytes plus each external-data location, digest, and declared bytes. The snapshot object, graph record, external-data array, and each external-data record are frozen. `createWebGpuSession()` uses only this snapshot after preflight for cache keys, network URLs, bounded byte expectations, digest verification, and ONNX Runtime `externalData` registration. It does not re-read `segment.path`, `segment.sha256`, `segment.externalData`, or any external entry field after the planner returns. The segment-1 result report also emits the already-owned external-data snapshot rather than revisiting the caller-owned manifest object.

The browser also bounds `split-manifest.json` itself before digesting or parsing it. `loadManifest()` routes the response body through `readResponseBytesBounded()` with a 4 MiB maximum, matching the atomic publisher's `MAX_PREVIOUS_MANIFEST_BYTES` / `MAX_STAGED_MANIFEST_BYTES` envelope. HTTP status handling, abort propagation, manifest SHA-256 measurement, JSON parsing, P0 validation, and later artifact-layout checks remain after that bounded read. A response that advertises or streams more than 4 MiB therefore fails before the excess bytes can be retained for hashing/parsing, and the harness no longer has an unbounded `response.arrayBuffer()` path for manifest consumption.

The verifier takes an owned shallow snapshot of the caller-provided plan before validating or constructing an accepted result. This is important for accessor- or Proxy-backed plans: `declaredBytes`, `requiredMaxBytes`, and `absoluteMaxBytes` must not be read once for validation and then read again with different values while the result is assembled. The captured values are used for both validation and the returned report, so an accepted report describes the same budget state that was actually checked.

The verifier does not trust limit values merely because they are present in that snapshot. `mode` must be `p0` or `absolute`, `absoluteMaxBytes` must equal the runtime 1 GiB hard limit, and `requiredMaxBytes` must equal the limit implied by the mode (256 MiB for `p0`, 1 GiB for `absolute`). A caller therefore cannot forge a larger plan envelope and then have the actual-byte verifier accept artifacts above the browser policy. The declared graph and external-data byte breakdown is also revalidated and must recombine exactly to `declaredBytes` before any artifact report field is read.

Artifact report ownership is also detached before arithmetic. The verifier first snapshots the `reports` array membership, then captures each report's `bytes` field exactly once, and finally performs validation and summation only from those owned primitive values. This prevents an earlier report's `bytes` accessor from replacing a later `reports[]` entry and changing which report participates in the same verification pass. Throwing accessors or Proxy traps during capture still fail closed.

The consumed byte fields must be safe integers with the required positivity constraints, the required limit cannot exceed the absolute limit, and declared bytes cannot exceed either runtime limit. Valid plans created by `planSegmentArtifactBudget()` keep the existing P0 (256 MiB) and absolute (1 GiB) behavior. Extra enumerable verifier-plan metadata is preserved in its owned shallow snapshot without re-reading the caller-owned object during result construction.

This contract does not promise recovery from arbitrary throwing Proxy traps during snapshot capture; those failures still fail closed. Issues #662, #666, and #668 remove repeated caller-owned reads across planning, validation, arithmetic, and result construction. The runtime-limit, byte-breakdown, browser-path preflight, planner-owned artifact-load snapshot, and bounded split-manifest consumption checks are additional reliability hardening for #167 and do not provide new real-model artifact-size, physical WebGPU memory, multi-browser relay/latency, or worker-loss evidence.
