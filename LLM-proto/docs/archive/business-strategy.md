# QJS ビジネス展開戦略：限定的機能の強みとしての位置づけ

## エグゼクティブサマリー

QJS（ブラウザ上でQuickJSを動かす分散サーバーレス実行環境）は、**「制約を前提とした計算インフラ」**という独自のポジションを確立できる。従来のサーバーレス（Lambda等）が「万能」を目指す中、QJSは「あえて制限されたユースケースに特化」することで、コスト・レイテンシ・スケーラビリティのトレードオフを最適化する。

## 1. 市場ポジショニング分析

### 1.1 既存サーバーレス市場の課題

| サービス | 強み | 弱み | コスト構造 |
|---------|------|------|-----------|
| **AWS Lambda** | 高可用性、豊富な統合 | コールドスタート遅延、高価格 | $0.20/百万リクエスト + 実行時間 |
| **Cloudflare Workers** | エッジ配置、低レイテンシ | CPU時間制限（50ms）、V8依存 | $5/千万リクエスト |
| **Deno Deploy** | シンプル、モダンJS | 新興、エコシステム未成熟 | $10/月〜 |
| **Vercel Edge** | Next.js統合、開発体験 | 機能制限、ベンダーロックイン | 従量課金 |

### 1.2 QJSの差別化ポジション

```
市場マップ（2x2マトリクス）

                    高レイテンシ許容
                           │
                           │
    高機能性 ──────────────┼────────────── 低機能性
    （Lambda）             │            （QJS）
                           │
                           │
                    低レイテンシ要求
                           │
              （Cloudflare Workers）
```

**QJSのポジション**: 機能性を限定（QuickJSサンドボックスのみ）し、その代わりに「コスト」と「スケーラビリティ」で圧倒的優位を築く。

### 1.3 重要：外部接続禁止ポリシー

**⚠️ セキュリティ上の理由により、QJS Worker（第三者のブラウザ）での外部接続は一切禁止されます。**

```
禁止API:
• fetch / XMLHttpRequest - HTTP/HTTPSリクエスト禁止
• WebSocket - リアルタイム通信禁止
• navigator.sendBeacon - ビーコン送信禁止
• WebRTC (DataChannel以外) - P2P通信制限
• DNSプリフェッチ - 事前解決禁止

許可される処理:
✓ 入力データの変換・整形
✓ 計算・検証・フィルタリング
✓ 暗号化・ハッシュ計算
✓ 正規表現処理
```

**踏み台攻撃防止**: もし外部接続を許可すると、攻撃者が悪意あるコードを登録し、他サイトへの攻撃に利用可能。これによりプラットフォーム全体のIPレピュテーションが低下し、法的責任問題が生じる。

**この制約により、以下のユースケースは対象外**:
- Webスクレイピング
- 外部API呼び出し
- ウェブクローリング
- データ収集（リアルタイム）

**対象となるのは純粋計算処理のみ**。

### 1.4 純粋計算処理のユースケース一覧

| カテゴリー | 具体例 | 禁止事項 |
|-----------|--------|---------|
| **データ変換** | JSON ↔ XML, CSVパース, Base64変換 | 外部APIからのデータ取得 |
| **検証・フィルタリング** | 正規表現マッチ, スキーマ検証, 入力検証 | 外部検証サービス呼び出し |
| **暗号化・ハッシュ** | SHA-256計算, JWT署名検証, チェックサム | 外部認証サーバー接続 |
| **数値計算** | 統計処理, 数値シミュレーション, レコメンド計算 | 外部データベース参照 |
| **コード変換** | フォーマット変換, Minify, Markdown→HTML | 外部リソースの動的取得 |
| **軽量画像処理** | メタデータ抽出, サイズ計算 | 外部画像URLの直接取得 |

**重要**: すべての入力データは事前に取得済みである必要がある。処理対象データはAPIリクエストボディまたはWebhookペイロードとして渡される。

## 2. ターゲットマーケット（優先度順）

### Tier 1: 高コスト負荷が問題になっている中規模企業

#### 2.1.1 データ変換・検証・整形（ETL前処理）
- **ペイン**: Lambdaで月額$5,000〜$20,000のデータ整形コスト（JSON→XML変換、CSVパース等）
- **QJSの提案**: 90%コスト削減、1/10の価格帯
- **利用形態**: APIレスポンスの整形、データ正規化、スキーマ検証
- **想定顧客**: SaaS企業、データ連携サービス、APIゲートウェイ運営
- **収益モデル**: 従量課金（Lambdaの1/10価格）
- **注意**: 外部接続は禁止。既に取得済みのデータ処理のみ対象

#### 2.1.2 バッチ処理・ETLパイプライン
- **ペイン**: 深夜のバッチ処理で高額なクラウド費用
- **QJSの提案**: 時間に依存しない分散処理（グローバルWorker利用）
- **利用形態**: ログ解析、データ変換、軽量フィルタリング
- **想定顧客**: SaaS企業、データ分析会社
- **収益モデル**: 月額定額 + 従量課金

#### 2.1.3 スパム判定・軽量検閲
- **ペイン**: ユーザーコンテンツの事前検閲コスト
- **QJSの提案**: 低コストで大規模並列判定
- **利用形態**: コメントフィルタ、画像メタデータチェック
- **想定顧客**: SNS運営、掲示板サービス、ECレビュー管理

### Tier 2: 技術的制約を受け入れられる開発者

#### 2.2.1 個人開発者・スタートアップ
- **ペイン**: クラウド請求の予測不能性、初期コスト
- **QJSの提案**: 超低コスト、予測可能な請求
- **利用形態**: バックエンド処理、Webhook処理
- **収益モデル**: フリーミアム（月1万回無料、その後従量）

#### 2.2.2 オープンソースプロジェクト
- **ペイン**: CI/CD費用、テスト実行コスト
- **QJSの提案**: 無料TierでCI実行、コミュニティ資源活用
- **利用形態**: テスト並列実行、ドキュメント生成
- **収益モデル**: スポンサーシップ、エンタープライズプラン

### Tier 3: 特殊要件を持つエンタープライズ

#### 2.3.1 データプライバシー重視企業
- **ペイン**: クラウドベンダーへのデータ送信リスク
- **QJSの提案**: エンドユーザーのブラウザで処理（データローカリティ）
- **利用形態**: 個人データのローカル前処理
- **想定顧客**: 医療、金融、規制厳しい業界
- **収益モデル**: エンタープライズライセンス

## 3. ビジネスモデル分析

### 3.1 収益モデルの選択肢

#### モデルA: 純粋なクラウドサーバーレス代行（推奨）
```
価格設定例:
┌────────────────────────────────────────────────┐
│ Free Tier                                      │
│ • 月10,000実行まで無料                         │
│ • 最大50ms実行時間                             │
│ • コミュニティサポート                         │
├────────────────────────────────────────────────┤
│ Pro Tier ($29/月)                              │
│ • 月100,000実行                                │
│ • 最大100ms実行時間                            │
│ • 優先Worker割り当て                           │
│ • メールサポート                               │
├────────────────────────────────────────────────┤
│ Business Tier ($149/月)                        │
│ • 月1,000,000実行                              │
│ • 最大200ms実行時間                            │
│ • 専用Workerプールオプション                   │
│ • SLA保証（99.9%）                             │
│ • 優先サポート                                 │
├────────────────────────────────────────────────┤
│ Enterprise (カスタム見積)                      │
│ • 無制限実行                                   │
│ • カスタムランタイム                           │
│ • 専用インフラ                                 │
│ • 24/7サポート                                 │
└────────────────────────────────────────────────┘
```

**メリット**:
- シンプルで顧客に理解しやすい
- 既存サーバーレス市場と比較可能
- スケールによる収益増

**デメリット**:
- Worker（ブラウザ閲覧者）のインセンティブとの両立が必要
- コスト構造が複雑（フォールバックLambda費用が変動）

#### モデルB: 二重課金モデル（Workerインセンティブ込み）
```
開発者 ← 使用料金 ───┐
                     ├→ プラットフォーム ← Workerへの報酬
企業 ← 使用料金 ────┘
```

**実装**: Worker（ブラウザ閲覧者）に対してマイクロペイメント
- 計算リソース提供に対する報酬
- トークンまたは法定通貨
- 透明性のある分散型台帳（オプション）

**メリット**:
- Workerの参加インセンティブを金銭化
- 「民主的」な分散コンピューティングの実現
- グローバルなWorker獲得が可能

**デメリット**:
- 規制リスク（未払い賃金、労働法）
- 複雑な送金インフラが必要
- 税務処理の複雑化

#### モデルC: SaaS統合モデル（推奨・中期）
- Next.js/Vercelプラグインとして提供
- WordPressプラグイン
- Shopifyアプリ
- 既存プラットフォームへの組み込み

**収益**: プラットフォーム手数料（30%）

### 3.2 コスト構造分析

#### 固定費用
| 項目 | 月額 | 備考 |
|------|------|------|
| ディスパッチャー（マルチマスター） | $500〜$2,000 | 3リージョン展開時 |
| Redis Cluster | $300〜$1,000 | Worker状態管理 |
| 監視・ロギング | $200〜$500 | Datadog等 |
| 開発・運用人件費 | $10,000〜 | 3名程度 |
| **合計** | **$11,000〜$13,500** | |

#### 変動費用（リクエストあたり）
| 項目 | 単価 | 備考 |
|------|------|------|
| Worker実行コスト | ~$0 | Workerの余剰リソース利用 |
| フォールバックLambda | $0.0000002 | Worker枯渇時のみ |
| CDN（コード配信） | $0.000001 | キャッシュ前提 |
| **合計** | **$0.0000012〜** | Lambdaの1/100程度 |

#### 損益分岐点計算
```
費用: $13,500/月（固定）+ $0.0000012×X（変動）
収入: $0.00002×X（Pro Tier想定単価）

損益分岐点 = $13,500 / ($0.00002 - $0.0000012)
         = 13,500 / 0.0000188
         = 718,085,106 実行/月
         ≈ 7.2億実行/月

→ リッチなEnterprise顧客獲得で早期黒字化が現実的
```

## 4. 技術的制約をビジネス強みに転換

### 4.1 「50ms実行制限」のポジショニング

#### 制約の裏返し：「高速処理の保証」
- **マーケティングメッセージ**: 「50ms以内に必ず応答。レイテンシ予測可能」
- **ターゲット**: リアルタイム性が重要なAPI、ゲームサーバー、チャット
- **差別化**: Lambdaのコールドスタート（数秒）とは対照的

#### ユースケース例
```javascript
// 高速スパム判定API（50ms以内）
function isSpam(content) {
  // 軽量なベイズフィルタ
  // 正規表現パターンマッチ
  // 外部API呼び出しなし
  return score > 0.8;
}
```

### 4.2 「QuickJSのみ」のポジショニング

#### 制約の裏返し：「セキュリティと予測可能性」
- **マーケティングメッセージ**: 「ネイティブモジュールなし。純粋なJavaScriptで安全」
- **ターゲット**: セキュリティ重視企業、コード監査が必要な業界
- **差別化**: サプライチェーン攻撃（npm compromise）のリスク低減

#### 制約を受け入れる開発者心理
- 「機能が少ない分、考えることが減る」→ シンプルさ志向
- 「子供に与えるおもちゃ」→ 破壊的なことはできない安心感
- 「制約は創造性を刺激する」→ ハッカー精神

### 4.3 「ブラウザ依存」のポジショニング

#### 制約の裏返し：「グローバル分散インフラ」
- **マーケティングメッセージ**: "The World's Largest Distributed Computer"
- **ターゲット**: グローバル展開する企業、地理的分散が必要な計算
- **差別化**: AWSのリージョン制限を超えたグローバルカバレッジ

## 5. 競合戦略

### 5.1 価格戦略

#### ペネトレーションプライシング（初期）
```
Lambda価格: $0.20/百万リクエスト
QJS価格:    $0.02/百万リクエスト（1/10）

メッセージ: "同じコードを10分の1の価格で"
```

#### 差別化要素
| 競合 | 彼らの強み | QJSのカウンター |
|------|-----------|----------------|
| Lambda | 統合、信頼性 | コスト、グローバル分散 |
| CF Workers | エッジ、速度 | 価格、純粋JSの安全 |
| Deno | モダン、シンプル | 既存ブラウザ資産活用 |

### 5.2 提携戦略

#### CDNプロバイダーとの提携
- **提案**: Cloudflare Workersの裏側でQJSをフォールバックとして利用
- **メリット**: Worker枯渇時のバックアップとしてQJS Workerプールを提供
- **収益**: Cloudflareからのバックアップ料金

#### Webホスティング会社との提携
- **提案**: cPanel等にQJS統合
- **メリット**: ホスティング顧客のブラウザをWorkerとして活用
- **収益**: ホスティング料金に上乗せ or 利益分配

## 6. リスクと課題

### 6.1 技術的リスク

#### Worker枯渇（最重大）
**シナリオ**: 夜間や特定地域でWorker（ブラウザ閲覧者）が不足
**影響**: フォールバックLambdaコスト増、SLA違反
**対策**:
- グローバル分散（タイムゾーン分散）
- Workerインセンティブ強化
- フォールバック自動スケーリング

#### セキュリティインシデント
**シナリオ**: 悪意あるWorkerが攻撃コードを実行
**影響**: プラットフォーム全体の信頼喪失
**対策**:
- 厳格なサンドボックス
- PBFTベースの結果検証
- 信頼性スコアリングと自動BAN

### 6.2 ビジネスリスク

#### 規制リスク
**懸念**: Workerへの報酬が「未払い労働」として問題視される可能性
**対策**:
- 法的レビュー（各国労働法）
- ボランティアベースの明確化
- 報酬をオプション化（感謝の気持ちの表明）

#### ビジネスモデルコピー
**懸念**: AWS等が同様のモデルを真似
**対策**:
- 特許出願（分散実行、結果検証アルゴリズム）
- 早期に市場シェア確保
- コミュニティ構築によるロックイン

### 6.3 市場リスク

#### 需要の低さ
**懸念**: QuickJSの制約が厳しすぎて需要がない
**対策**:
- MVPでの早期検証（PoC開発者プログラム）
- 制約緩和のロードマップ（WASI対応等）

## 8. まとめ：成功の鍵

QJSのビジネス成功は以下の3点に依存：

### 1. 制約を「強み」として伝える
「50ms」「QuickJSのみ」は欠点ではなく**「予測可能で安全な計算環境」**という価値提案。

### 2. ニッチから始める
万能なLambdaの代替ではなく、**コストが問題になっている特定ユースケース**（データ変換・検証、バッチ処理）に集中。

### 3. 信頼を最初に構築
セキュリティインシデントは致命傷。最初の1年は**完璧なサンドボックスと透明性**で信頼を獲得。

> "unzenは、世界中のブラウザを世界最大の分散コンピュータに変換する。
> 企業は90%コスト削減を実現し、開発者は予測可能な請求を得る。
> インターネットの余剰計算リソースを、民主的でオープンなインフラに再定義する。"
