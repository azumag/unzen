## 1. 課題認識: 現行方針の市場競争力

### 1.1 推論API市場の価格崩壊（2026年2月時点）

30Bクラスモデルの推論価格は年10倍のペースで下落している。

| プロバイダ | Input/M tokens | Output/M tokens | 速度 | インフラ |
|---|---|---|---|---|
| DeepInfra | $0.05-0.08 | $0.20-0.40 | 中速 | GPU (H100/A100) |
| Fireworks AI | ~$0.13 | ~$0.13 | 300-430 t/s | GPU (H100/H200/MI300X) |
| Together AI | ~$0.10-0.20 | ~$0.26-0.60 | 中速 | GPU (H100/Blackwell) |
| Groq | $0.11 | $0.34 | 1,200 t/s | カスタムLPU |
| Cerebras | $0.10 | $0.10 | 1,800 t/s | Wafer-Scale Engine |
| Cloudflare Workers AI | $0.03-0.05 | $0.20-0.34 | N/A | Edge GPU（小型モデルのみ） |

PLAN.md 4.1項のAPI販売単価 $0.001/1K tokens = **$1.00/M tokens** は、最安プロバイダの**5〜20倍**。
30Bクラスの推論を「安さ」で売る戦略は、GPU/LPU/WSEベースのプロバイダに勝てない。

### 1.2 価格下落を加速する3要因

1. **カスタムシリコン**: Groq LPU（GPU比10x省電力）、Cerebras WSE-3（GPU比7,000xメモリ帯域幅）
2. **NVIDIA Blackwell GPU**: GPU系プロバイダに4-10xのコスト削減をもたらしている
3. **MoEモデルの普及**: Qwen3-30B-A3B（活性化パラメータ3Bのみ）で同品質が10倍安く動作

### 1.3 分散推論の直接競合

| プロジェクト | 方式 | 規模 | 備考 |
|---|---|---|---|
| Petals | GPUノード間パイプライン並列 | ボランティアGPU | 4-6 t/s (70B)。ACL 2023 |
| Prime Intellect | P2P (RTX 4090〜H200) | 1,250+ GPU実績 | 暗号学的検証（TOPLOC v2） |
| AI Grid | ブラウザタブをGPUノード化 (WebGPU) | 実験段階 | コンセプトがunzenに最も近い |

## 2. 発想の転換: 計算量増幅がタダという武器

### 2.1 核心的な非対称性

```
中央集権プロバイダ: 計算量 × N = コスト × N
unzen（ブラウザ分散）: 計算量 × N ≈ コスト × 1
```

ブラウザ訪問者の余剰GPUを使うため、**並列に走らせるインスタンス数を増やしてもunzen側の計算コストは増えない**。
「計算量を増やして品質を上げる」テクニックを、中央集権プロバイダには不可能なコスト構造で提供できる。

### 2.2 ポジションの転換

```
Before: 「30Bモデルを安く使える」→ DeepInfra ($0.05/M) に勝てない
After:  「GPT-4oレベルの品質を$0.10-0.50/Mで」→ GPT-4o ($10/M) の1/20-1/100
```

## 3. 実現手段: 学術的根拠

### 3.1 Mixture-of-Agents (MoA)

**出典**: Wang et al., "Mixture-of-Agents Enhances Large Language Model Capabilities", ICLR 2025

6つのOSSモデルを3レイヤー構成で組み合わせ、各レイヤーの出力を次レイヤーの入力として精錬する。

**AlpacaEval 2.0 勝率**:

| モデル | LC Win% |
|---|---|
| MoA (OSS only, 6 proposers × 3 layers) | **65.1** |
| GPT-4o | 57.5 |
| GPT-4 Turbo | 55.0 |
| Qwen1.5-110B-Chat (単体) | 43.9 |

- OSSモデルの集団がGPT-4oを**+7.6%**上回る
- MT-Bench: MoA (OSS) 9.25 vs GPT-4o 9.19
- Proposer多様性の効果: 6種のモデル vs 同一モデル6コピーで+4.6%の差
- レイヤー間は逐次、レイヤー内は**完全並列**

### 3.2 Best-of-N サンプリング

N個の回答を生成し、リワードモデルで最良を選択する。

| モデル (GSM8K) | N=1 | N=4 | N=16 | N=64 |
|---|---|---|---|---|
| Llama-3.2-3B | 42.0% | 61.0% | 70.8% | 70.8% |
| Llama-3.1-8B | 53.6% | 69.0% | 77.0% | 79.2% |

- 3Bモデルでもサンプル数16で+29%の精度向上
- N=16以降は収穫逓減（リワードハッキングのリスクもある）
- ブラウザ側でPairRM（0.4B）を実行すれば選択コストもゼロ

### 3.3 Self-Consistency（多数決）

CoTで複数の推論パスをサンプリングし、最終回答を多数決で選ぶ。

| ベンチマーク (PaLM-540B) | N=1 (CoT) | N=40 (SC) | 改善幅 |
|---|---|---|---|
| GSM8K | 56.5% | 74.4% | **+17.9%** |
| AQuA | 35.8% | 48.3% | **+12.5%** |

- 効率化手法（RASC等）により、N=8で標準N=40の品質を達成可能

### 3.4 "More Agents Is All You Need" (TMLR 2024)

同じLLMのN個のインスタンスで独立生成→投票。

- GPT-3.5 + ZS-CoT + N=40 → GSM8K **88%** = GPT-4単独と同等
- Llama2-13B at N=15 ≈ Llama2-70B at N=1 (GSM8K)
- 異種モデル混合でさらに品質向上（35%→47%、困難タスク）

### 3.5 LLMルーティング (RouteLLM, ICLR 2025)

クエリの難易度に応じてモデルを動的選択する。

- GPT-4の品質の95%を維持しながら、GPT-4呼び出しを**74%削減**
- ルーターのオーバーヘッド: GPT-4生成コストの+0.4%以下

## 4. unzenへの適用: アンサンブル推論アーキテクチャ

### 4.1 基本構成

```
┌──────────────────────────────────────────┐
│  API Customer                            │
│  "量子コンピュータについて説明して"         │
└──────────────────┬───────────────────────┘
                   │
          ┌────────▼────────┐
          │  Coordinator     │
          │  RouteLLM で     │
          │  難易度判定       │
          └────────┬────────┘
                   │
     ┌─────────────┼─────────────┐
     │ 簡単        │ 中程度      │ 難しい
     ▼             ▼             ▼
  1ノード       Best-of-4      Full MoA
  単独推論      4ノード並列     6+ proposers
  (~35秒)      + PairRM選択    → aggregator
               (~35秒)        (~70-105秒)
```

### 4.2 各ノードの役割

```
各ブラウザノード:
  - 7B-8Bモデルを1台で完結実行（4-bit量子化 ≈ 3.5GB VRAM）
  - WebLLMが既にブラウザ内7B推論を実証済み
  - ノード間の依存関係なし（完全独立）

Aggregator（MoA使用時）:
  - 別のブラウザノードがproposer群の出力を受け取り精錬
  - または、Coordinator側でサーバー集約

リワードモデル（Best-of-N使用時）:
  - PairRM (0.4B, DeBERTa-v3-large) をクライアント側WebGPUで実行
  - または、Unigram Consistency Score（モデル不要の統計的選択）
```

### 4.3 パイプライン分割方式との比較

| 側面 | パイプライン分割（PLAN.md現行） | アンサンブル（本案） |
|---|---|---|
| ノード間依存 | 直列（1→2→...→8） | **なし（完全独立）** |
| チェックポイントリレー | 必須・複雑 | **不要** |
| 障害復旧 | パイプライン全体再構成 | **1提案が減るだけ** |
| 最小ノード数 | 8固定 | **1から動作** |
| VRAM/ノード | ~2.1GB | ~3.5GB |
| レイテンシ | ~35秒（直列） | ~35秒（並列、1レイヤーMoA時） |
| 提供モデル品質 | 30Bクラス相当 | **GPT-4oレベル（MoA時）** |
| Coordinator複雑度 | 非常に高い | **中程度** |
| セキュリティ | チェックポイント改竄リスク | **各ノード独立検証** |
| MVP実装工数 | 非常に大きい | **大幅に小さい** |

### 4.4 経済性

```
GPT-4oレベルの品質を提供する場合のコスト比較:

  OpenAI GPT-4o:        $2.50 (input) / $10.00 (output) per M tokens
  中央集権MoA (18回推論): $0.03 × 18 = $0.54/M tokens
  unzen MoA:            計算コスト ≈ 0（ブラウザ訪問者負担）
                        → API価格 $0.10-0.50/M で十分な利益

  GPT-4o比: 1/20 〜 1/100 の価格
  中央集権MoA比: 同等価格だがunzen側の原価がほぼゼロ
```

**注意**: 上記は理論値。実際の品質はproposerモデルのサイズ（7B vs 70B+）に依存し、
MoA論文が使用した70B+モデルと同じ品質を7Bモデルで再現できるかは未検証。
ただし、"More Agents Is All You Need" の結果（13B × N=15 ≈ 70B × N=1）は、
小型モデルの数で大型モデルの品質に迫れる可能性を示している。

### 4.5 PLAN.md 既存設計との関係

本案はPLAN.md v2.6の以下の設計をそのまま活用できる:

- **1.2項 通信ポリシー**: 変更不要。各ノードはCoordinatorとのみ通信
- **1.2項 安全境界**: 変更不要。CSP/サンドボックス/COOP-COEPはそのまま適用
- **2項 ビジョン**: 変更不要。広告のカウンターパートという位置づけは同じ
- **3項 UX設計**: 変更不要。オプトインモデルは同じ
- **4.5項 長時間ワーカー**: そのまま適用可能。Tier階層化も有効

変更が必要な箇所:

- **5項 技術設計**: パイプライン→アンサンブルへの変更（または併存）
- **4.1項 RPM試算**: API単価の前提が変わる（高品質＝高単価が可能）
- **5.3項 パラメータ設計**: セグメント分割→独立ノード実行への変更

## 5. リスクと未検証事項

### 5.1 品質に関するリスク

- MoA論文のproposerは70B+モデル。7Bモデルでどこまで品質が出るかは未検証
- Best-of-Nの品質はリワードモデルの精度に依存。PairRM (0.4B) のブラウザ実行時の性能は未実測
- ベンチマーク（AlpacaEval, GSM8K等）での改善が、実際のAPI利用パターンに転移するかは不明

### 5.2 技術的リスク

- 7B 4-bit量子化（~3.5GB）がWebGPU経由で十分な速度で動くかはデバイス依存
- MoA aggregatorへの入力が大きい（6提案のコンテキスト連結）→ コンテキスト長の制約
- 異種モデル（Qwen/Llama/Gemma/Mistral）のブラウザ互換WebGPU実装が必要

### 5.3 市場リスク

- レイテンシ30-105秒はリアルタイム用途に不適。バッチ/非同期市場の規模は要調査
- 中央集権プロバイダもMoAを提供し始めた場合、GPU価格下落で価格優位が縮小し得る
- Together AI Batch API（50%OFF）との直接競合

### 5.4 パイプライン方式との併存の可能性

本案とPLAN.md現行のパイプライン方式は排他ではない:

- **Phase 1**: アンサンブル方式でMVP（実装が簡素、早期に市場検証可能）
- **Phase 2**: 需要と技術が成熟したらパイプライン方式で単一大型モデルも追加
- 同一Coordinatorインフラ上で両方式を共存させることは可能
